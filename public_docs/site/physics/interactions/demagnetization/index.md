# Demagnetization

Demagnetization is the non-local magnetostatic interaction generated by magnetic charge. This
document defines the physical contract once and then records the distinct FDM/FEM and CPU/GPU
realizations. A backend implementation is not allowed to change the sign, units, observable names,
or requested model semantics defined here.

(demag-root-problem-statement)=
## Physical problem

Let $\Omega_m$ be the magnetic body and let $\mathbf M$ be its magnetization. The demagnetizing
field is the field produced by $\mathbf M$ in the magnetostatic limit. It is non-local: changing
magnetization in one cell changes the field at every other cell. FullMag exposes the field as
`H_demag` in $\mathrm{A\,m^{-1}}$ and the interaction energy as `E_demag` in $\mathrm{J}$.

The common contract covers open boundaries. A periodic problem is a different Green-function
problem and is therefore documented in {doc}`periodic-demag`; it must not be silently approximated
by a finite open box.

(demag-root-governing-equations)=
## Governing equations

The magnetostatic equations are

```{math}
:label: eq-demag-maxwell
\nabla\times\mathbf H_{\mathrm d}=\mathbf 0,
\qquad
\nabla\cdot(\mathbf H_{\mathrm d}+\mathbf M)=0.
```

For a simply connected open-boundary problem, introduce the scalar potential
$\mathbf H_{\mathrm d}=-\nabla\phi$. Then

```{math}
:label: eq-demag-potential
\nabla^2\phi=\nabla\cdot\mathbf M\quad\text{in the magnetostatic domain},
\qquad
\mathbf H_{\mathrm d}=-\nabla\phi.
```

The interaction energy and its variational derivative are

```{math}
:label: eq-demag-energy
E_{\mathrm d}[\mathbf M]
=-\frac{\mu_0}{2}\int_{\Omega_m}\mathbf M\cdot\mathbf H_{\mathrm d}\,\mathrm dV,
\qquad
\mathbf H_{\mathrm d}=-\frac{1}{\mu_0}\frac{\delta E_{\mathrm d}}{\delta\mathbf M}.
```

The factor $1/2$ is part of the self-interaction convention. It must be preserved by FDM energy
reductions and FEM field-to-energy reductions.

(demag-root-symbols-and-si-units)=
## Symbols and SI units

| Symbol | Definition | SI unit |
|---|---|---:|
| $\mathbf M$ | magnetization | $\mathrm{A\,m^{-1}}$ |
| $\mathbf H_{\mathrm d}$ | demagnetizing field | $\mathrm{A\,m^{-1}}$ |
| $\phi$ | magnetic scalar potential | $\mathrm{A}$ |
| $\mu_0$ | vacuum permeability | $\mathrm{N\,A^{-2}}$ |
| $E_{\mathrm d}$ | demagnetization energy | $\mathrm{J}$ |
| $\Omega_m$ | magnetic domain | $\mathrm{m^3}$ |
| $\Omega_a$ | FEM airbox domain | $\mathrm{m^3}$ |
| $\mathbf n$ | outward unit normal | $1$ |
| $\sigma_m$ | surface magnetic charge density $\mathbf M\cdot\mathbf n$ | $\mathrm{A\,m^{-1}}$ |
| $G$ | continuous demagnetization Green kernel | $\mathrm{m^{-3}}$ |
| $\delta E_{\mathrm d}/\delta\mathbf M$ | functional derivative of demagnetization energy | $\mathrm{N\,m^2\,A^{-1}}$ |

(demag-root-assumptions-and-validity)=
## Assumptions and validity

- The model is continuum magnetostatics with no displacement-current term.
- $\mathbf M$ is bounded and represented by the selected FDM grid or FEM finite-element space.
- Open-boundary calculations must represent the exterior through an analytically correct convolution,
  a sufficiently resolved FEM airbox, or a boundary-integral realization.
- A finite airbox is not mathematically identical to infinity; its boundary condition and size are
  part of the numerical model and must be reported.
- A periodic calculation uses a periodic kernel or periodic FEM reduction and cannot be qualified by
  comparing it only with an open-boundary result.

(demag-root-python-api)=
## Python authoring and complete parameter reference

```python
# %% FEM demagnetization stage scenario
import fullmag as fm

study = fm.study("demag_fem_poisson_robin")
study.engine("fem")
study.device("cpu", precision="double")
study.mode("strict")
study.interactive(True)
study.universe(
    mode="manual",
    size=(1200e-9, 600e-9, 550e-9),
    center=(0.0, 0.0, 0.0),
    padding=(0.0, 0.0, 0.0),
)
study.universe.mesh(
    minimum_element_size=10e-9,
    maximum_element_size=110e-9,
    maximum_element_growth_rate=1.9,
    grading="geometric",
)
film = study.geometry(fm.Box(size=(500e-9, 125e-9, 3e-9), name="film"), name="film")
film.Ms = 8.0e5
film.Aex = 1.3e-11
film.alpha = 0.02
film.m = fm.init.UniformMagnetization((1.0, 0.1, 0.0))
film.mesh.thin_film(
    minimum_element_size=3e-9,
    maximum_element_size=3e-9,
    layers=1,
    topology="prismatic",
    exact_layers=True,
    transition="pyramid_to_tetrahedra",
    order=1,
)
study.demag(realization="poisson_robin")
study.fem_demag_solver(
    solver="CG",
    preconditioner="AMG",
    rtol=1e-12,
    max_iterations=600,
)
# The planner materializes the shared FEM domain mesh when the first stage is run.
study.stages.add_relax(
    stage_id="relax",
    algorithm="nonlinear_cg",
    max_steps=50_000,
    tolT=0.5e-8,
).autosave(
    fm.StageAutosave(
        table=fm.TableAutosave(
            every_steps=10,
            quantities=["step", "e_demag", "e_total", "max_torque_T"],
        ),
        fields=[fm.FieldAutosave("H_demag", every_steps=100)],
    )
)
```

This is the public execution pattern. The selected airbox realization, FEM Poisson solver policy,
mesh, stage, and autosaves are declared on `study`; the planner then lowers the stage snapshot and
records the resolved runtime separately. The FDM equivalent uses `study.engine("fdm")`,
`study.cell(...)`, and the documented `FDMDemag` policy rather than constructing a direct
top-level problem object in the user script.

(demag-root-problem-ir)=
## ProblemIR and planner contract

`Demag.to_ir()` lowers only the interaction realization. It does not select a device, allocate an
airbox, or pretend that a future model is executable. `FDMDemag.to_ir()` carries the FDM convolution
policy. `FdmPbc.to_ir()` carries periodic-axis intent. The planner combines these values with the
requested backend and installed capabilities.

The planner must preserve both **requested intent** (`model`, `variant`, periodic policy, FDM
strategy) and **resolved execution** (solver, device, precision, concrete realization). A request for
`periodic_airbox_k0` with FDM is a validation error, not permission to fall back to `open`.

(demag-root-round-trip-and-failure-semantics)=
## Round-trip and failure semantics

Canonical Python export must reproduce the requested model and policy, not merely the resolved
backend. Validation errors must identify the invalid parameter and the unsupported combination.
Examples include mixing `model` with the legacy `realization`, passing `variant` to `bem`, using
`image_counts` without `truncated_images`, and requesting the FEM-only periodic airbox policy on
FDM. Unsupported combinations are reported as unsupported combinations; no silent fallback is
allowed.

(demag-root-discrete-realization)=
## Discrete realizations

| Realization | Discretization | Boundary treatment | Device distinction |
|---|---|---|---|
| FDM convolution | Cell-centered grid and Newell demag tensor | Open convolution padding; optional truncated images | CPU reference FFT and CUDA FP32/FP64 kernels |
| FEM Poisson airbox | H1 scalar potential on magnetic body plus airbox | Dirichlet or Robin outer boundary | CPU MFEM/Hypre and GPU stage dispatch |
| FEM/BEM | FEM volume unknowns coupled to boundary integral | Open exterior represented by boundary operator | CPU implementation; GPU qualification is separate |
| Periodic demag | Periodic kernel or reduced periodic FEM system | Periodic classes and zero-mode policy | FDM truncated images and FEM periodic-airbox policy differ |

(demag-root-implementation-mapping)=
## Implementation mapping

The implementation is intentionally split by responsibility. FDM owns convolution and spectra;
FEM CPU owns Poisson/BEM assembly, solve, field recovery, energy, and cache lifecycle; FEM GPU owns
stage dispatch and reductions. The source index below is the authoritative path-plus-symbol map.

(demag-root-validation)=
## Validation status

The validation programme must compare field and energy, not only one scalar. It includes uniform
magnetized rectangular bodies, thin films, multilayer stacks, open-boundary FEM/FDM comparisons,
periodic zero-mode cases, CPU/GPU parity at the same precision, and mesh/airbox convergence. A
passing unit test without executed-device evidence does not qualify the GPU lane.

(demag-root-limitations)=
## Limitations and qualification boundaries

The public API exposes `bem` and `fmm` vocabulary, but a vocabulary entry is not proof that every
solver/device combination is production-qualified. The planner must reject an unavailable
realization. Airbox truncation, periodic zero-mode treatment, mixed-element FEM meshes, and GPU
execution require explicit qualification evidence recorded in provenance.
