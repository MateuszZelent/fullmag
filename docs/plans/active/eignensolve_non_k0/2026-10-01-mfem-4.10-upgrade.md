# Aktualizacja MFEM 4.10 — wykonanie i bramki

## Zakres

Użytkownik zlecił podniesienie MFEM do 4.10 podczas integracji eigensolve.
Zmiana obejmuje FEM CPU, FEM GPU i CUDA-free prefix workera SLEPc runtime-v2.
FDM nie otrzymuje zmian. Relaksacja, eigensolve i stare wyniki #188 zachowują
swoje dotychczasowe źródła i obrazy; aktualizacja zależności nie rekwalifikuje ich.

- Tag object: `16b0b814a3ba15a56c7a04e02d047188800cc0bf`.

## Wdrożone źródłowo

1. `docker/fem-cpu/Dockerfile`: 4.7→4.10, kontrola SHA po clone,
   C++17, MFEM_ENABLE_TESTING=OFF i build wyłącznie targetu mfem.
2. `docker/fem-gpu/Dockerfile`: 4.9→4.10 w obu prefixach, kontrola SHA,
   C++17, MFEM_ENABLE_TESTING=OFF, zachowane osobne CUDA/CPU biblioteki.
3. `scripts/local_runner/Dockerfile.build`: CPU_MFEM_ONLY=1 pobiera ten sam
   pełny commit4.10 zamiast starego4.9; zachowane testyOFF i CPU prefix.
4. Generowany `readme.md` zaktualizowany przez właściciela dashboardu wersji.

Nie zmieniono hypre, libCEED, PETSc, SLEPc ani konfiguracji aktywnego runnera.
Przegląd użycia API nie znalazł ProjectGrad/getKnotLocation/findKnotSpan/
FindMaxima/FindInterpolant/CheckBdrPatches/Getl1Diag w natywnym FEM.
Ten ograniczony scan nie zastępuje kompilacji przeciw nowemu MFEM.

## Skutki numeryczne

MFEM4.10 zastępuje reguły simplex dodatnimi wagami (triangle0–25, tet0–20).
Dlatego samo numerowanie rzędu nie dowodzi identyczności z historycznym MFEM.
F01 nadal wymaga usunięcia order1 dla prism6. Polityka tet5/prism4 ma zachować
zgodność źródeł z dotychczasowymi obrazami, aż powstaną nowe receipty.
Digest musi wiązać rzeczywistą geometrię, FEorder, requested/resolved quadrature
order i GetNPoints; audyt opiera się na danych rzeczywistych, nie stałych liczbach.
Przy zmianie rodziny reguł powtórzyć kontrolę matrix/nullspace/residual oraz
zbieżności siatki/airboxu i signed DE/BV. Nie zmieniać Aex ani progów residualu.

Upstream zmienił również default HyprePCG. Sprawdzone ścieżki demag CPU FK i
GPU Poisson ustawiają SetTol i SetMaxIter jawnie; pozostałe wywołania i wykonanie
należy objąć review/buildem. Complex mixed forms z4.10 nie zastępują obecnego
operatora Floqueta automatycznie. GPU-request nie może otrzymać CPU fallbacku.

## Wykonalna trasa operatorska

Kolejka udostępnia `verify-source` i `build`, bez operacji budowy obrazów.
Udokumentowany `just runner-build-image` jest osobną trasą operatorską.
Przed budową potwierdzić brak aktywnych jobów, zwolnienie lease oraz zdrowie runnera;
nie uruchamiać równoległego ciężkiego buildu. Następnie:

1. Wybrać zweryfikowany lokalny toolchain i nowy tag workera.
2. Wykonać `just runner-build-image <toolchain> <nowy-tag> 1 default`.
3. Sprawdzić immutable image ID, faktyczną wersję MFEM, CPU HYPRE,
   nagłówki, CMake config i dynamiczny loader; CPU prefix ma pozostać bez CUDA.
4. Powiązać nowy digest z profilem runtime-only, zachowując historyczne obrazy.
5. Zlecić build przez kolejkę z pełnym SHA źródeł; odebrać terminalny receipt.
6. Sprawdzić hash i wersję załadowanej biblioteki MFEM w provenance, następnie
   wykonać pilota CPU. GPU otrzymuje odrębny obraz i bramkę wykonania.

Historyczny worker runtime-v2 zawiera `libmfem.so.4.9.0`. Sam hash biblioteki
nie zastępuje jawnego potwierdzenia wersji nowej zależności. Aktualizacja
konfiguracji nie dowodzi przebudowy ani wdrożenia.

iteracji HyprePCG. Przegląd wszystkich sześciu miejsc konstrukcji HyprePCG

nie dodatkowymi miejscami konstrukcji. Zmiana tych dwóch defaultów nie jest
zatem powodem zmiany konfiguracji Fullmaga w sprawdzonych ścieżkach.
To review źródeł; nie dowodzi identyczności wyników między wersjami MFEM.
Nie zmieniono progów residualu, parametrów materiałowych ani wyboru CPU/GPU.
