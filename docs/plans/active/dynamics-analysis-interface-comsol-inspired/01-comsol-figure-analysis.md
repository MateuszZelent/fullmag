## Core COMSOL UI Construction

COMSOL uses a stable four-surface construction:

1. `Model Builder` tree on the left.
2. `Settings` property grid for the selected tree node.
3. `Graphics` viewport for geometry and result plots.
4. `Results` tree nodes for datasets, derived values, tables, plot groups, and animations.

This is the central pattern. The module does not create a separate bespoke UI
for every scientific analysis. Instead, the meaning is encoded in:

- the selected tree node,
- the active Settings sections,
- the selected study step,
- the selected dataset / solution parameter,
- the expression being plotted,
- the result plot type.

The important design point is that `Study` and `Results` are first-class tree
families, not hidden tabs. A user can inspect how a result was generated by
walking the tree.

## Settings Panel Pattern

Every selected node exposes a structured Settings panel:

- `Label`
- selection scope: domain, boundary, geometry, or physics interface
- optional `Override and Contribution`
- `Equation`
- `Basic Properties`
- `Model Input`
- solver/study settings
- dependent-variable inheritance
- result expression and dataset settings
- coloring/range/style

The panel is dense. It uses collapsible sections and exact field labels rather
than explanatory marketing text.

### Frequency-Domain Physics Settings

The frequency-domain physics figure shows:

- static material and interaction parameters,
- `equilibrium magnetization m0`,
- `static external field h0`,
- `dynamical external field delta h`,
- dependent variables named `dmX`, `dmY`, `dmZ`,
- equation view available for audit.

> **Key physics constraint from COMSOL manual**: In frequency-domain studies, the dynamic drive field `δh` is specified as a **phasor amplitude** (A/m), not as a time-domain waveform. The solver automatically supplies the harmonic factor `e^{iωt}`. Users must not include explicit `sin(ωt)` or `cos(ωt)` terms in drive field definitions. This affects how the Driven Response Inspector presents drive source parameters.

Fullmag equivalent:

- Inspector must show equilibrium source and resolved `m0`,
- drive source and phase/amplitude,
- selected component / complex view,
- solver convention and provenance,
- not only a generic "frequency response" label.
- equilibrium state must be validated as physically current: mesh revision match, material revision match, max torque norm below threshold, and staleness detection if source state was modified after the dynamics solve.
- if driven frequency response study has no dynamic perturbation `δh` configured, Inspector must show a blocking validation error — the frequency-domain response will be identically zero without excitation.

## Study Step Pattern

### Eigenfrequency and Floquet Sweeps

The COMSOL `Eigenfrequency` and Floquet settings screenshots expose:

- command buttons: `Compute`, `Update Solution`,
- solver: `ARPACK` (or sparse direct eigensolvers like MUMPS),
- eigenfrequency search method: manual search, search around a specified frequency, or closest in absolute value,
- desired number of eigenfrequencies to solve,
- unit selector, e.g. `GHz` or `rad/s`,
- `Search for eigenfrequencies around` (essential for shifting and scaling methods in magnonic crystal band gaps),
- physics/variables solve selection: active/passive status for coupled equations (e.g. micromagnetics coupled to RF/elasticity),
- Floquet Wave Vector ($\mathbf{k}_F$) components: $k_{Fx}$, $k_{Fy}$, $k_{Fz}$ in SI units (`rad/m`) (used for periodic boundary wave-vector sweeps),
- dependent-variable values.

The key UX idea: modal analysis setup is not just "run". It is a visible contract: how many modes, around which frequency, at which wave-vector ($\mathbf{k}_F$), which physics (e.g., exchange-only, demag-disabled, or full DMI), and from which initial/static state.

### Frequency Domain and Parameter Sweeps

The driven frequency-domain screenshots expose:

- the frequency-domain study step,
- selected physics interfaces to solve,
- solver configuration with stationary / parametric sweeps (e.g., sweeping excitation frequency $f$ or wavevector $k$),
- dependent-variable inheritance: importing magnetization state $\mathbf{m}_0$ and static field $\mathbf{h}_0$ from a previous time-domain relaxation or stationary study,
- frequency sweep as the controlling parameter.

### Multiphysics Magnon-Polaron Coupling Lesson

From pages 48-51 of the manual, COMSOL demonstrates coupled Solid Mechanics and Frequency Domain Micromagnetics. This introduces:
- Bidirectional coupling: magnetization precession ($\delta \mathbf{m}$) drives elastic deformation ($\mathbf{u}$), and elastic waves drive magnetization.
- Multi-component dispersion curves: plotting dispersion showing the *anticrossing* (repulsion) of magnon branches and phonon branches.
- **UI & Solver Gating Warning**: While the dispersion chart and UI structures must be designed to accommodate multiple branches and magnon-polaron Hybridized modes, this is a *target layout contract* and does *not* imply immediate backend solver support. Coupled multiphysics lanes must be strictly capability-gated via `frequency_domain.coupled.solid_mechanics` and displayed as `unsupported` or `degraded` if the active backend solver does not provide the coupled operator.

Fullmag equivalent:

- driven sweep inspector must show requested frequency range/samples,
- excitation source and its spatial distribution (e.g. antenna geometry),
- solved physics lanes (e.g., micromagnetics, elastic coupling, heat transfer),
- inherited equilibrium resource (with validation check on mesh/geometry alignment),
- resolved execution lane (e.g., CPU, GPU, or degraded path due to unsupported nonzero-k demag),
- partial/degraded status.

## Results Pattern

COMSOL results are constructed from:

- a dataset,
- a solution parameter such as eigenfrequency,
- an expression such as `dmX`,
- a plot type such as Surface,
- a color table/range.

The eigenmode figure on page 30 is especially important. It shows `Surface`
Settings with:

- `Dataset: Study 1/Solution 1`,
- `Solution parameters: Manual`,
- `Eigenfrequency: ... GHz`,
- `Expression: dmX`,
- `Unit`,
- color table and legend controls.

This is the direct visual precedent for Fullmag's target controls:

- selected mode/frequency,
- selected component,
- selected complex view,
- selected field resource,
- selected colormap/range,
- selected overlay target.

## Spectrum And Peak Pattern

The magnetostatic thin-film figure shows a result composition rather than a raw
solver log:

- left: physical geometry and applied field orientation,
- middle: spectrum chart `Amplitude (a.u.)` versus `f (GHz)`, where `a.u.` denotes the spatially-averaged magnitude of the dynamic magnetization response $\langle |\delta \mathbf{m}| \rangle$ in arbitrary (solver-normalized) units,
- peaks marked with labels such as `4.1 GHz`, `4.7 GHz`, `5.6 GHz`,
- right: spatial mode/response maps for each selected peak.

This is the most important UX target for Fullmag dynamics analysis.

The Fullmag equivalent should not force users to infer peaks from a generic
line chart. A professional view must place the spectrum and spatial fields in
one coordinated workflow:

- select peak in chart,
- inspect exact row in table,
- show corresponding field payload,
- compare against modal eigenfrequency when available,
- preserve provenance and units.

## What COMSOL Does Well

- It makes the tree of physics, studies, solvers, and results visible.
- It keeps node settings inspectable and editable in one property grid.
- It treats result plots as explicit expressions over explicit datasets.
- It makes study steps and solver settings first-class.
- It shows dependent-variable inheritance clearly for frequency-domain work.
- It has a natural path from a spectrum peak to a spatial mode map.

## What Fullmag Should Improve

COMSOL is powerful but indirect. Fullmag should keep the construction logic and
make dynamics-specific workflows easier:

- show FMR/modal/driven mode explicitly instead of requiring tree archaeology,
- expose `δmx / δmy / δmz / |δm|` and complex view as first-class controls,
- give one synchronized spectrum/peak/field workbench,
- show backend capability and artifact provenance inline,
- avoid mixing amplitude, phase, power, susceptibility, and residuals on one
  axis without explicit selectors or split axes,
- use resource revisions instead of hidden solution-state mutation.
