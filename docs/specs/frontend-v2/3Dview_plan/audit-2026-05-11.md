# Audit 3Dview_plan - 2026-05-11

## Current Status After Plan Correction

The audit findings below have been absorbed into the corrected canonical plan:

- `README.md` defines which files are implementation authority.
- `implementation_plan.md` is now the implementation-ready Phase 5 plan.
- `scratch/01-viewport-architecture.md` through `scratch/05-testing-performance.md` are aligned to one R3F viewport.
- `docs/specs/frontend-v2/14-viewport-3d-module.md` is aligned to one R3F viewport.
- imported `*.resolved*` files are marked superseded and must not drive implementation.

The current plan no longer leaves renderer choice, multi-pane scope, API facade, cache, invalidation, lifecycle, FDM/FEM mapping, airbox, picking, CPU budget, or memory gates as open questions. They are explicit implementation deliverables and gates.

## Verdict

Pierwotny plan nie byl gotowy do bezpiecznej implementacji "od razu". Kierunek byl dobry: resource-first API, osobne zasoby topologii/pol, rozdzielenie adapterow domenowych od renderera, dirty-driven rendering i testy pamieciowe. Decyzja architektoniczna po audycie: targetem Phase 5 jest jeden viewport R3F, bez podzialu/split viewportu i bez multi-pane w pierwszej implementacji.

Najwazniejszy wniosek z pierwotnego audytu: zanim zaczniemy implementowac 3D viewport, trzeba bylo zamknac kontrakt API/cache/lifecycle oraz zaktualizowac kanoniczna specyfikacje `docs/specs/frontend-v2/14-viewport-3d-module.md` pod R3F. Ten wniosek zostal przeniesiony do poprawionego `implementation_plan.md` jako Phase 5a.

## Przyjeta decyzja po audycie

1. Implementujemy jeden viewport 3D oparty o R3F.
2. Nie implementujemy podzialu viewportu, multi-pane, split-h/split-v, quad ani wielu `<Canvas>` w tym etapie.
3. Kamera, selection, layer state i quantity state nadal ida przez kernel/resource contracts, ale render surface jest jeden.
4. R3F jest akceptowane jako warstwa sceny, ale musi miec jawny odpowiednik polityki lifecycle: dispose zasobow, cache budzetowany, context loss recovery i testy braku wyciekow.
5. `14-viewport-3d-module.md` trzeba zaktualizowac, bo obecnie opisuje renderer imperatywny jako kanoniczny.

## Co plan dobrze ustawia

1. Renderer ma konsumowac model renderowania, a nie surowe payloady API.
2. Topologia, pola i stan wizualizacji sa rozdzielone na osobne zasoby.
3. Przelaczenie quantity ma wymieniac bufor pola, nie przebudowywac topologii.
4. Selection ma isc przez kernel, a nie przez importy miedzy modulami.
5. Plan rozpoznaje potrzebne API hooks: `useDomainMeta`, `useMeshTopology`, `useFieldData`, `useVisualizationState`, `useSceneObjects`.
6. Backend ma juz wazne endpointy: domain meta/topology, field vector samples, visualization state, shared-domain manifest/topology, per-object/per-part topology.
7. Testy pamieci, idle frame count i stress switch 2D/3D sa dobrym kierunkiem.

## P0 - blokery architektury

### P0.1 Renderer: R3F wybrane, ale specyfikacja kanoniczna nadal jest stara

`3Dview_plan` zaklada `three`, `@react-three/fiber`, `@react-three/drei` i komponenty typu `<ObjectMeshLayer>`. To jest przyjety kierunek. Problemem nie jest juz wybor R3F, tylko dryf specyfikacji: kanoniczna specyfikacja `14-viewport-3d-module.md` nadal opisuje:

- `SceneController.ts`,
- `MeshLayerRenderer.ts`,
- `FieldSurfaceRenderer.ts`,
- `VectorGlyphRenderer.ts`,
- `WebglResourceTracker.ts`,
- `BufferPool.ts`,
- imperatywne klasy warstw,
- jawny context loss rebuild,
- jawne release topologii i buforow.

To jest sprzecznosc kontraktu, nie detal stylistyczny. Skoro R3F jest decyzja docelowa, trzeba poprawic specyfikacje i plan lifecycle tak, aby R3F nie bylo pretekstem do utraty kontroli nad WebGL resources.

Rekomendacja dla raportu i planu:

- zaktualizowac `14-viewport-3d-module.md` pod jeden R3F viewport;
- usunac z planu warianty split/multi-pane/wiele `<Canvas>`;
- opisac R3F-equivalent dla `WebglResourceTracker` i `BufferPool`;
- zostawic wymog: field update nie przebudowuje topologii, topology revision zwalnia geometrie, unmount zwalnia wszystkie zasoby, context loss odbudowuje scene z aktualnego render modelu.

### P0.2 Multi-pane zostaje wyjete z aktualnego zakresu

Plan w kilku miejscach zaklada wiele `<Canvas>` i wspolna kamere. To zostaje odrzucone dla Phase 5. Jeden R3F viewport oznacza jeden canvas i jeden WebGL context.

Dla duzych FEM/FDM to dobra decyzja: wiele canvasow pomnozyloby geometrie, materialy, atrybuty kolorow i glyph buffers przez liczbe paneli. W pierwszej wersji nie ma zadnego uzasadnienia, zeby placic ten koszt.

Rekomendacja dla raportu i planu:

- usunac layouts `split-h`, `split-v`, `quad`, `one-plus-two`;
- usunac shared camera across panes, bo nie ma panes;
- zostawic jeden camera state dla jednego viewportu;
- jesli multi-view wroci w przyszlosci, musi przejsc oddzielny ADR/performance audit, najlepiej jako single-canvas scissor viewports, nie wiele WebGL contextow.

### P0.3 "Cuboids vs tetrahedra is the only difference" jest zbyt mocne

To zdanie jest niebezpieczne. Rzeczywiste roznice FDM/FEM obejmuja:

- regularna siatke bez binarnej topologii dla FDM vs jawna topologia FMMT dla FEM;
- wartosci na komorkach/siatce vs wartosci wezlowe FEM;
- interpolacje i probing FEM, ktory nie jest prostym `fieldValues[cellIdx]`;
- object/part/airbox scopes tylko dla FEM endpointow;
- element markers i boundary markers, ktore nie sa stabilnym `objectIndex == marker`;
- FDM meta obecnie zwraca `origin=[0,0,0]`, `spacing=[1,1,1]`, bounds z samego grid shape, wiec nie mozna jeszcze zakladac fizycznych wymiarow SI dla FDM.

Rekomendacja: poprawic zalozenie na: "renderer jest domenowo neutralny, ale adaptery musza jawnie modelowac roznice topologii, lokalizacji pol, probingu, mapowania obiektow i jednostek".

### P0.4 Frontend API facade nie istnieje w wymaganej formie

`ControlRoomApi` ma obecnie tylko:

- `sessions.current.status()`,
- `commands.detail/list/submit()`,
- prywatne JSON requesty przez wygenerowany transport.

Nie ma jeszcze publicznych metod:

- `data.domain.meta()`,
- `data.domain.topology()`,
- `data.fields.vector()`,
- `visualization.state()/patch()`,
- `model.scene()/universe()`,
- `meshing.sharedDomainManifest()/topology()`,
- `meshing.objectTopology()/partTopology()`.

Nie ma tez binarnego request helpera dla 200/204/304, ETag, `If-None-Match`, content-type, abort, diagnostics i contract-version.

Plan w `scratch/04-domain-adapters.md` pokazuje `api.fetchBinary("/v2/...")`, czyli raw endpoint string w hooku. To lamanie resource-first API hygiene. Endpoint stringi musza zostac w warstwie API facade, nie w module viewportu.

### P0.5 OpenAPI typuje 304, ale nie typuje `If-None-Match`

Backend obsluguje `If-None-Match` w `conditional_binary_response`, a wygenerowane typy maja odpowiedzi 304 dla topologii i pol. Jednoczesnie operacje w `openapi-v2-types.ts` maja `header?: never`, wiec frontend nie ma typowanego sposobu przekazania `If-None-Match`.

Rekomendacja: albo poprawic OpenAPI parametry naglowkow dla zasobow cacheowalnych, albo w `ControlRoomApi` stworzyc jawny nizszy helper `requestBinaryResource`, ktory kontroluje `If-None-Match` i pozostaje jedynym miejscem raw fetch.

## P1 - braki w refresh/invalidation

### P1.1 `useResource` nie jest jeszcze cachem zasobow

`useResource` ma abort on unmount i reaguje na `ResourceInvalidationController`, ale nie ma:

- ETag store,
- 304 reuse poprzedniego payloadu,
- inflight dedupe,
- byte budget,
- retain/release,
- dispose hook dla WebGL/typed arrays,
- resource family keying dla `quantity/component/scope`.

Dla viewportu 3D to za malo. Przy polach i topologiach binarnych hook musi rozroznic "not modified" od "ready with new data" i nie moze trzymac starych ArrayBufferow bez limitu.

### P1.2 Realtime bridge jest za ogolny dla viewportu

`RealtimeInvalidationBridge` invaliduje `session:status` i `recommended_fetch` jako string. To wystarcza dla prostych zasobow, ale viewport 3D potrzebuje deterministycznej mapy:

- `topology_revision`/`mesh_revision` -> topology resources,
- `field_revision` + `quantity/component/scope` -> field vector resources,
- `visualization_state_revision` -> visualization state,
- `scene_revision` -> scene/universe/object metadata,
- selection change -> selection overlay/probe only, bez refetch pola.

Plan wspomina revisions, ale nie definiuje resource keys ani testow, ze niepowiazana invalidacja nie odswieza duzego pola.

### P1.3 `load` callbacks moga powodowac nadmiarowe odswiezenia

`useResource` ma `load` i `resolveRevision` w dependency array. Jezeli hooki viewportu beda tworzyc callbacki inline bez `useCallback`, beda refetchowac przy renderach Reacta. Plan musi jawnie wymagac stabilnych loaderow i testu "React rerender without revision change does not refetch binary".

## P1 - braki CPU/performance

### P1.4 FDM instanced cuboids dla kazdej komorki nie jest bezpieczny jako domysl

Plan opisuje `InstancedMesh` z macierza dla kazdej komorki i `cellCenters`. To jest kosztowne:

- 1M komorek to okolo 64 MB samych `instanceMatrix` w Float32,
- kolejne bufory ida na kolory, indeksy, centra, glyphy i scalar/vector values,
- 10M komorek staje sie nierealne w przegladarce.

Rekomendacja: FDM musi zaczynac od budzetowanego render resource: downsample/LOD na wejscu, impostory/slice/surface extraction albo backend/client decimation zanim powstana pelne macierze instancji.

### P1.5 Kolory i glyphy nie moga byc liczone glownie na main thread

Plan zaklada `applyColormap()` i subsampling glyphow w React/R3F memo. Dla duzych pol to bedzie przycinalo UI i bedzie trudne do anulowania przy szybkim przelaczaniu quantity.

Rekomendacja: Phase 5a/5b musi dodac:

- worker albo chunked scheduler dla dekodowania/projekcji kolorow/glyph selection,
- abort/cancel dla przestarzalych rewizji,
- buffer pool dla kolorow i pozycji glyphow,
- pomiar czasu transformacji buforow, nie tylko FPS.

### P1.6 FEM Float64 -> Float32 bez polityki zwalniania buforow

FMMT/FMVP dekodery zwracaja widoki `Float64Array`/`Uint32Array` na oryginalny `ArrayBuffer`. Renderer potrzebuje zwykle `Float32Array`. Bez polityki transfer/release latwo trzymac jednoczesnie:

- oryginalny binary buffer,
- dekodowane widoki,
- przekonwertowane Float32 GPU upload buffers,
- stare bufory po poprzedniej rewizji.

Rekomendacja: `ResourceCache` musi miec ownera i dispose policy. Po zbudowaniu render buffers trzeba wiedziec, czy binary ArrayBuffer zostaje cacheowany dla ETag/304, czy jest zwalniany po utworzeniu stabilnego render resource.

## P1 - braki domenowe

### P1.7 Mapowanie obiektow przez marker == index sceny jest bledne

Plan w `04-domain-adapters.md` sugeruje, ze FEM markers odpowiadaja indeksom obiektow w kolejnosci sceny. Backend ma lepszy kontrakt w `MeshPartResource`: `role`, `object_id`, `geometry_id`, `material_id`, `boundary_face_indices`, `node_indices`, `surface_faces`.

Renderer nie powinien zgadywac mapowania z markerow. Powinien korzystac z manifestu shared-domain/per-part i backendowego object/part mapping.

### P1.8 Picking/probing wymaga dodatkowego kontraktu

FMMT zawiera `boundaryFaces`, `elementMarkers`, `boundaryMarkers`, ale nie zawiera jawnego `boundary_face_to_element`. Dla klikniecia w powierzchnie FEM nie wystarczy sam `faceIndex`, jesli chcemy:

- wskazac element,
- zrobic probe wartosci pola,
- zinterpolowac wartosc z wezlow,
- rozroznic object/part/airbox bez zgadywania.

Rekomendacja: przed implementacja probingu dodac albo endpoint probe/hit-test po stronie backendu, albo rozszerzyc topologie o stabilne mapowanie boundary face -> element/object/part.

### P1.9 Airbox nie jest `SceneObject`

Plan traktuje airbox miejscami jak obiekt sceny z `isAirbox`. Aktualny kontrakt wskazuje airbox przez mesh part `role="air"`, `scope_kind=airbox`, visualization layer `airbox` i universe resource. Renderer musi uzywac tych kontraktow, a nie oczekiwac `isAirbox` w scene object.

## P2 - braki testow i higieny dokumentow

### P2.1 Komendy testowe w planie nie istnieja jeszcze

Plan wymienia `pnpm --dir apps/control-room run audit:idle-performance`, ale `package.json` nie ma takiego skryptu. Nie ma tez zaleznosci `three`, `@react-three/fiber`, `@react-three/drei`, `@react-three/test-renderer`.

### P2.2 Test "heap returns to baseline" jest zbyt kruchy

JS GC nie daje deterministycznej gwarancji powrotu heap do identycznej wartosci po stress tescie. Lepsze kryteria:

- bounded high-water mark,
- liczba aktywnych resource owners po unmount == 0,
- liczba WebGL geometries/materials/textures po unmount == 0,
- brak wzrostu po N cyklach powyzej tolerancji,
- explicit byte budget dla cache.

### P2.3 Katalog planu zawiera pliki, ktore beda mylic kolejne agenty

W katalogu sa metadata, stare `.resolved.*`, duplikaty i `:Zone.Identifier`. To jest operacyjny problem, bo przyszly agent moze przeczytac stary wariant i wdrozyc inna architekture.

Rekomendacja: po zatwierdzeniu audytu zostawic jeden canonical plan plus ewentualnie `scratch/README.md`, a stare warianty przeniesc do archiwum albo usunac z tego katalogu.

## Poprawiona kolejnosc wdrozenia

### Phase 5a - contract lock before renderer

1. Zapisac decyzje "single R3F viewport" w `14-viewport-3d-module.md`, `implementation_plan.md`, `01-viewport-architecture.md`, `02-render-pipeline.md`, `03-multi-viewport-layout.md` i `05-testing-performance.md`.
2. Dodac typed API facade dla binary/json viewport resources.
3. Dodac `requestBinaryResource` z 200/204/304, ETag, `If-None-Match`, diagnostics, contract-version, abort.
4. Dodac resource keys:
   - `data:domain:meta`,
   - `data:domain:topology`,
   - `data:field-vector:{quantity}:{component}:{scopeKind}:{scopeId}`,
   - `visualization:state`,
   - `model:scene`,
   - `model:universe`,
   - `meshing:shared-domain:manifest`,
   - `meshing:shared-domain:topology`,
   - `meshing:part-topology:{partId}`,
   - `meshing:object-topology:{objectId}`.
5. Dodac cache z ETag, inflight dedupe, byte budget i release/dispose callbackami.
6. Dodac testy: 304 reuse, abort, unrelated invalidation no-refetch, quantity switch no topology fetch.

### Phase 5b - domain adapters without WebGL

1. Adapter FDM bez pelnego instancjonowania milionow komorek jako domyslu.
2. Adapter FEM oparty o shared-domain manifest/mesh parts, nie marker index.
3. Jednolity render model z field location, interpolation/probe strategy i object/part scopes.
4. Testy geometry builderow, LOD i mapowania object/part/airbox.

### Phase 5c - single R3F renderer lifecycle

1. Implementacja jednego R3F canvasu.
2. Jawny R3F-equivalent resource tracker z mierzalnym dispose.
3. Context loss recovery test.
4. Idle render audit.
5. Memory stress z budzetami, nie tylko snapshot heap.

### Phase 5d - deferred multi-view decision

1. Nie implementowac multi-pane w Phase 5.
2. Usunac multi-pane z kryteriow gotowosci biezacego etapu.
3. Jesli potrzeba wielu widokow wroci, przygotowac osobny ADR z pomiarem CPU/GPU/memory i preferencja single-canvas scissor viewports.

## Minimalne kryteria "gotowe do implementacji"

Plan bedzie gotowy dopiero gdy spelnia wszystkie punkty:

- decyzja "single R3F viewport" jest zapisana w canonical spec i master plan;
- API facade nie wymaga raw endpoint stringow poza `ControlRoomApi`;
- binary resources obsluguja 200/204/304, ETag i `If-None-Match`;
- cache ma byte budget i dispose policy;
- revision/resource key mapping jest jawny i testowany;
- FDM large grid nie buduje domyslnie pelnego per-cell matrix buffer;
- FEM object/part/airbox mapping uzywa mesh manifest, a nie zgadywania markerow;
- picking/probing ma jawny kontrakt albo jest ograniczony do selection bez wartosci pola;
- plan nie zawiera split/multi-pane/wielu `<Canvas>` w Phase 5;
- package scripts zawieraja realne gate'y wymienione w planie.

## Decyzja audytu

Nie wdrazac `viewport-3d` wedlug starych wariantow planu ani plikow `*.resolved*`. Wdrazac wedlug poprawionego `implementation_plan.md`, w ktorym dawne blokery API/cache/invalidation/lifecycle zostaly przeniesione do Phase 5a jako pierwsze deliverables i gates. Dopiero po Phase 5a wdrazac single R3F renderer.
