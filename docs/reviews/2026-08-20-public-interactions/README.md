# Public interaction documentation audit and revision pack

This directory contains a source-aware audit of FullMag's public documentation for magnetic
interactions, direct torques, stochastic drives, transport-coupled fields, and inter-region
couplings. The review covers both:

- `public_docs/site/physics/interactions/**`, and
- `public_docs/site/python-api/interactions/**`.

The files in `proposed/` are review-ready Markdown revision briefs. Each file can be used as the
content specification for a canonical public page update. They deliberately live outside
`public_docs/site` until the associated page, source map, executable example, and strict Sphinx
build can be changed atomically.

## Executive verdict

The physical core is substantially stronger than the presentation quality suggests. Exchange,
Zeeman, anisotropy, bulk/interfacial DMI, Brown noise, prescribed-strain magnetoelasticity,
local SOT, and the stated spin-transport constitutive laws are mostly internally consistent with
the declared SI and sign conventions. The documentation is nevertheless not yet publication-safe
as one coherent reference because correctness claims, API examples, capability status, and source
ownership are inconsistent between pages.

### Release-blocking findings

1. **DMI contains broken MyST/LaTeX tokens.** Symbols such as `Omega_m`, `mathbf M`, and
   `mathrm{J}` have lost their backslashes. The page also presents a stage shell that does not
   register DMI, followed by a hand-written DMI `ProblemIR` fragment described as though it came
   from the example.
2. **The Oersted documentation has two incompatible owners.** The physics page describes the
   closure-aware solved-current FEM OE-F1/OE-F2 family, while the Python API page still describes
   an older prescribed-density/midpoint planner and uses obsolete DSL calls such as
   `study.discretization`, `study.material`, and `study.current_module`.
3. **The inter-region example does not construct left and right regions.** Both region boxes are
   centred at the origin, so they overlap. They must be translated by opposite half-widths.
4. **The demagnetization bibliography misidentifies the Newell tensor paper.** The correct
   publication is A. J. Newell, W. Williams, and D. J. Dunlop, *Journal of Geophysical Research:
   Solid Earth* **98**(B6), 9551–9555 (1993), DOI `10.1029/93JB00694`.
5. **Public Python examples are not executed by documentation CI.** The workflow invokes
   `scripts/check_public_doc_examples.py` without `--execute`; consequently an AST-valid example
   can use removed or incompatible API calls and still pass the generic example gate.
6. **Front-matter status overclaims complete support.** Several pages use `status: implemented`
   while their own capability matrices say `semantic_only`, `partial`, `unsupported`, or expose
   no complete stage-first registration path.
7. **The documentation contract requires globally duplicated labels.** Bare labels such as
   `(problem-statement)=` cannot safely be reused across Sphinx pages. The effective repository
   practice—namespaced labels—should be made the formal rule.

## Cross-cutting corrections

Every canonical interaction page should use the following structure:

1. physical problem and owner;
2. governing energy/field/torque equations;
3. complete symbol and SI-unit table;
4. sign, orientation, frame, and normalization conventions;
5. assumptions and validity limits;
6. capability matrix for FDM/FEM × CPU/GPU, with separate authoring, planning, execution, and
   qualification states;
7. one minimal stage-first example that is executed in CI;
8. canonical `ProblemIR` fragment generated by the serializer, not manually approximated;
9. discrete realization and boundary/interface treatment;
10. observables and units;
11. deterministic or statistical validation cases with expected outcomes;
12. limitations, roadmap, bibliography, and source-code index.

### Required status vocabulary

Use one status per capability row rather than one optimistic page-wide adjective:

| Status | Meaning |
|---|---|
| `semantic_only` | Python/IR can represent the request, but no strict executable lane exists. |
| `reference_executable` | A bounded reference implementation runs; production and broad qualification are not claimed. |
| `production_executable` | The production path runs for the stated envelope; scientific validation remains separate. |
| `validated` | The declared numerical and physical validation suite passes for the stated envelope. |
| `unsupported` | The request fails closed for this lane. |

A page may retain a summary status only if it is the least permissive accurate description of the
public workflow. `implemented` must not mean merely that a kernel source file exists.

### Required example policy

- Run `python scripts/check_public_doc_examples.py --root public_docs/site --execute` in CI.
- Execute every interaction example in an isolated `fm.reset()` context.
- For examples that require an unavailable public registration method, publish no pseudo-runnable
  shell. Show a constructor/IR inspection fixture outside the executable-example class and state
  the missing API explicitly.
- Keep realistic first-use examples short. Move full serialized `ProblemIR`, RT0 closure fixtures,
  and expert transport graphs to downloadable assets or dedicated advanced pages.
- Add expected values or invariants. Construction alone is not validation.

### Required provenance policy

Each scientific page should record:

- authored interaction and parameter values;
- normalized axes and frames;
- requested solver, device, precision, and execution mode;
- resolved algorithm/realization and capability decision;
- source/material/mesh revisions where another module supplies the field or torque;
- qualification evidence identifier and tolerance policy.

## Validation priority

### P0 — documentation integrity

- strict Sphinx build with unique namespaced labels;
- parse and execute every Python block;
- compare documented constructor tables with live signatures;
- generate and compare documented IR fragments with serializer output;
- reject stale links and source-map symbols.

### P1 — field/energy consistency

For every conservative interaction, verify the discrete directional derivative

```math
\frac{E(\mathbf m+\varepsilon\boldsymbol\eta)-E(\mathbf m-\varepsilon\boldsymbol\eta)}{2\varepsilon}
\approx
-\mu_0\sum_i M_{s,i}\,\mathbf H_i\cdot\boldsymbol\eta_i\,w_i
```

for decreasing `epsilon`, with tangent variations and the lane's actual integration weights.

### P1 — direct torque consistency

For STT, SOT, and transport torque, verify:

- tangent property `m · T = 0` to numerical tolerance;
- odd/even behaviour under current, polarization, and interface-normal reversal;
- exactly one Gilbert-to-explicit conversion;
- linear drive scaling in the small-signal regime;
- CPU/GPU parity under a declared precision-specific tolerance.

### P1 — stochastic consistency

For thermal noise, validate distributional properties rather than trajectory identity:

- component mean and variance;
- spatial and temporal independence policy;
- fixed-seed replay within one lane;
- accepted-step/rejected-step random-draw semantics;
- equilibrium macrospin distribution and timestep weak convergence.

## Scope boundary and evidence

This is a documentation-and-source audit at commit
`f79c65d43ef2ac550f89932b47940489f719acb0`. It does not claim native solver execution,
CUDA device execution, convergence qualification, or experimental validation. Where a current
page claims a backend capability, this pack preserves the narrowest evidence-backed statement and
marks stronger claims as gates to be demonstrated.
