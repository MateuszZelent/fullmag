# Zależności host storage w trasach Docker DEV

Audyt statyczny kodu w worktree z 31.10.2026; nie uruchamiałem Dockera ani buildów. Opisuje trasę źródłową, nie kwalifikuje działającego runtime.

## Wniosek

`just docker-dev-toolchain` kieruje build obrazu do BuildKit i zapisuje receipty oraz log operacji w nazwanym wolumenie BuildControl; nie odkłada kompilatora, stagingu ani logów builda w project host storage. Wcześniej identyfikacja Compose przez `build_volume_toolchain` wymagała `fullmag_storage.resolve_layout` i poprawnego host storage root/markera. Dodałem źródłowe API `compose_source_identity(repo_root)` oparte na Git i istniejącym formatterze oraz podłączyłem je do `build_volume_toolchain` i `prepare-development-images`, usuwając to sprzężenie dla tych callerów. Osobno `resolve_defaults` może czytać opcjonalny zapis ustawień w `index/docker-host-settings.json` przy wyborze domyślnego source i portu.

just docker-dev to build-backend-plus-runtime. Host storage jest mu potrzebny dla per-run session/results i trwałych workspace settings użytkownika. Nie wolno ich usuwać jako cache. Kod kieruje build/cache/control i logi operacji do Docker volumes; initialize_runtime tworzy tylko małą przestrzeń runtime, nie legacy builds/cache/tmp/frontend.

## Trasy i host storage

- justfile:27-32 uruchamia bootstrap z --direct-development. just_storage_shell.sh:209-220 przepuszcza tę komendę przed generic prepare-links/runner. Aktywna funkcja bootstrap_docker_toolchain.build od razu deleguje do build_volume_toolchain (bootstrap_docker_toolchain.py:513-515); starsza gałąź z initialize_host_storage i hostowym lockiem to ścieżka bez tego przełącznika, nie recepta just.
- Build-only potrzebuje zarejestrowanego checkoutu, Git i hashy tracked dependency inputs (bootstrap_docker_toolchain.py:100-117, docker_build_control.py:853-858), plus .env/process toolchain args (bootstrap_docker_toolchain.py:352-357). To są źródła i konfiguracja builda.
- Zbędny odczyt storage: docker_build_control.py:812-820 robi storage.resolve_layout przed identyfikatorem. Resolver czyta FULLMAG_PROJECT_STORAGE_ROOT/.env i marker (fullmag_storage.py:325-351); project/worktree identity powstają z Git i storage.identifier. Nowa funkcja docker_compose_identity.compose_source_identity omija resolver, odrzuca submodule i checkout spoza worktree_records, a następnie wywołuje wspólny formatter. Funkcja została podłączona do build_volume_toolchain i prepare-development-images. Bootstrap direct-development zachowuje wybór źródeł z Git/process/.env przez resolve_defaults(include_host_settings=False), bez odczytu indeksu host-settings. Potwierdzono zgodność tożsamości worktree z dawną ścieżką także przy wskazaniu nieistniejącego Z:\missing-docker-build-storage.
- Stan bazowy: bootstrap_docker_toolchain.py:685-695 wywoływał resolve_defaults; ta funkcja czyta .env oraz opcjonalnie storage-root/index/docker-host-settings.json (docker_dev_defaults.py:200-218,243-257) dla source/port. Port nie wpływa na build toolchain; host settings mogą natomiast wskazywać source. To osobne wejście konfiguracji do oceny przy wymaganiu pełnej niezależności od storage. Komentarz just_storage_shell.sh:215 jest nieaktualny dla direct route: aktywna ścieżka przygotowuje BuildControl i lease w Docker, nie host global heavy lock.
- BuildKit używa checkoutu jako Compose context, a stan operacji zapisuje do /control w nazwanym wolumenie (docker_build_control.py:666-695,708-722,812-900). Nie ma host build directory/log/staging w tej gałęzi.

Dla just docker-dev:

- justfile:36 i just_storage_shell.sh:454-572 kierują docker_dev.py up do docker_dev_up.ensure_up; nowa grupa uruchamia docker_volume_dev.start (docker_dev.py:2466-2477, docker_dev_up.py:1249-1269). To ścieżka startu backendu i frontendowego UI, nie samo budowanie obrazu toolchain.
- docker_dev.py:_select_source woła resolve_layout i initialize_runtime (docker_dev.py:931-940). Initializer tworzy/odczytuje marker, używa .initialize.lock, tworzy katalogi index/locks i tylko runs_root; nie materializuje legacy build/cache/tmp/frontend roots (fullmag_storage.py:560-614). index/locks są tu efektem wspólnego initializer-a; aktywny start używa leases/receiptów BuildControl w Docker. Host fullmag-heavy.lock występuje w legacy direct-recreate (docker_dev.py:1033-1076,2432-2444), nie w wywołaniu up. Komentarz wrappera o host-lock admission (just_storage_shell.sh:568) opisuje starą ścieżkę, nie aktualne up.
- Host session/results są prawdziwym runtime input/output: start tworzy runs/<worktree>/docker-volume-dev/<attempt> i host certificate (docker_volume_dev.py:2141-2162), po czym montuje je jako /state; trwałe storage/user-data/<compose-project> jest /user-data (docker_volume_dev.py:2277-2314, fullmag_docker_runtime.py:870-884, compose.dev.yaml:214-220). Zachować session, wyniki i workspace.db/settings.
- Źródło i Git common directory są bind-mounted read-only (compose.dev.yaml:175-182); są koniecznymi live inputs. FULLMAG_SCRIPT_OUTPUT_DIRECTORY może dodać jawny bind writable do wskazanego dziecka checkoutu dla wyników skryptów (docker_script_output_mounts.py:8-56); to dane użytkownika. local_volume(storage_root/state) robi Windows local-drive/filesystem/reparse/capacity attestation (docker_volume_dev.py:1930,2223, windows_folder_host.py:386-421), nie host build write.
- Private/compiler, frontend build, control/receipt i nowy group-ledger stan są Docker volumes; nowy render wybiera group ledger, retained legacy receipt może przypinać host ledger (docker_volume_dev.py:722-779,880-915,1049+). Docker service logs są limitowane w Docker logging driver (docker_volume_dev.py:2491). Konkretnie zbędny argument: _backend_cache podaje layout['storage_root'] jako runroot do cache.prepare (docker_volume_dev.py:741,768), ale _plan go nie używa i jawnie trzyma receipt w named volume (docker_backend_volume_cache.py:468-575). Usunięcie tego argumentu nie powinno zmieniać host danych.
